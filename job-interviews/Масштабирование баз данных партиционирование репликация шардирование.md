# Масштабирование баз данных: партиционирование, репликация, шардирование

Гайд для Lead/Senior PHP backend developer: как объяснять на интервью, как выбирать подход на практике и какие trade-off'ы важно видеть заранее.

## Карта темы

- Вертикальное и горизонтальное масштабирование.
- Масштабирование чтения и записи.
- PostgreSQL partitioning: range/list/hash, pruning, индексы, constraints, maintenance.
- Репликация: physical/logical, sync/async, streaming, read replicas, lag, failover, split-brain.
- Шардирование: стратегии, shard key, resharding, cross-shard операции, global IDs.
- Consistency и distributed transactions.
- ClickHouse, Redis Cluster, RabbitMQ в контексте масштабирования.
- PHP/Laravel/Symfony: роутинг соединений, транзакции, миграции, очереди, observability.
- Backups, disaster recovery, чеклисты и вопросы для самопроверки.

## 1. Базовая модель масштабирования

### Вертикальное масштабирование

Вертикальное масштабирование: увеличить ресурсы одного узла: CPU, RAM, NVMe, IOPS, network bandwidth.

Плюсы:

- Самый простой путь: минимум изменений в приложении.
- Хорошо работает до определенного предела.
- Нет распределенных транзакций и cross-node latency.

Минусы:

- Есть физический и бюджетный потолок.
- Один узел остается крупной точкой отказа, если нет HA.
- Апгрейды могут требовать downtime или сложной миграции.

Короткий senior-ответ:

> Сначала я почти всегда проверю вертикальное масштабирование и оптимизацию запросов: индексы, query plan, connection pooling, vacuum, настройки памяти. Горизонтальное масштабирование дороже организационно и добавляет distributed systems problems.

### Горизонтальное масштабирование

Горизонтальное масштабирование: добавить узлы и распределить нагрузку.

Основные варианты:

- Read replicas для масштабирования чтения.
- Partitioning для управления большими таблицами внутри одной БД.
- Sharding для распределения данных и записи между независимыми узлами.
- Caching для снятия части read-нагрузки.
- CQRS/materialized views/search/analytics stores для специализированных read-моделей.

Главный trade-off:

> Горизонтальное масштабирование повышает capacity, но добавляет сложность: routing, consistency, failover, observability, backups, migrations, rebalancing.

## 2. Read scaling vs write scaling

### Масштабирование чтения

Типовые инструменты:

- Индексы и оптимизация запросов.
- Кеширование: Redis, CDN, application cache.
- Read replicas.
- Materialized views и denormalized read models.
- Search/analytics storage: Elasticsearch/OpenSearch, ClickHouse.

Особенности read replicas:

- Реплики обычно eventually consistent.
- Возможен replication lag.
- Read-after-write может ломаться, если сразу после записи читать с реплики.
- Нужен routing: критичные чтения после записи направлять на primary или использовать sticky primary window.

### Масштабирование записи

Типовые инструменты:

- Батчинг и асинхронная обработка.
- Уменьшение contention: меньше hot rows, меньше глобальных счетчиков.
- Partitioning для maintenance и уменьшения локальных индексов.
- Шардирование, если один primary не справляется с write throughput.
- Outbox/event-driven подход для разгрузки синхронного пути.

Короткий senior-ответ:

> Read scaling часто решается репликами и кешами. Write scaling сложнее: один primary все равно принимает запись. Если оптимизация, batching и partitioning не помогают, нужен sharding или изменение модели записи.

## 3. PostgreSQL partitioning

Partitioning в PostgreSQL делит одну логическую таблицу на несколько физических partition-таблиц. Приложение обычно работает с parent table, а PostgreSQL направляет строки в нужные partitions.

Важно:

- Partitioning не равен sharding.
- Все partitions находятся в рамках одного PostgreSQL-кластера, если не используются отдельные расширения/FDW/распределенные решения.
- Partitioning чаще решает проблему больших таблиц, maintenance, retention и query pruning, а не бесконечное write scaling.

### Типы partitioning

#### Range partitioning

Деление по диапазону значений.

Примеры:

- `created_at` по месяцам.
- `id` по диапазонам.
- временные event/log таблицы.

Когда подходит:

- Данные естественно идут по времени.
- Частые запросы фильтруют по диапазону.
- Нужен быстрый retention: `DROP TABLE partition` вместо массового `DELETE`.

Риск:

- Последняя partition может стать hot partition при интенсивной записи по текущему времени.

#### List partitioning

Деление по списку значений.

Примеры:

- `country_code`.
- `region`.
- `tenant_tier`.
- тип события.

Когда подходит:

- Небольшой и понятный набор категорий.
- Запросы часто фильтруют по категории.

Риск:

- Слишком много значений приведет к большому количеству partitions.
- Новые значения требуют создания partition или default partition.

#### Hash partitioning

Деление по hash от ключа.

Примеры:

- `user_id`.
- `tenant_id`.
- `account_id`.

Когда подходит:

- Нужно равномерно распределить нагрузку внутри таблицы.
- Нет удобного range/list признака.

Риск:

- Плохо для range queries.
- Сложнее менять количество partitions.

### Partition pruning

Partition pruning: PostgreSQL исключает ненужные partitions из плана запроса.

Пример:

```sql
SELECT *
FROM events
WHERE created_at >= '2026-06-01'
  AND created_at < '2026-07-01';
```

Если `events` partitioned by range по `created_at`, PostgreSQL должен читать только partition за июнь 2026.

Что важно для pruning:

- В запросе должен быть фильтр по partition key.
- Условия должны быть понятны планировщику.
- Функции над partition key могут мешать pruning: `date(created_at) = ...` хуже, чем range condition.
- Prepared statements иногда влияют на качество планов; надо проверять `EXPLAIN (ANALYZE, BUFFERS)`.

Короткий senior-ответ:

> Partitioning полезен только если запросы реально отсекают partitions. Если большинство запросов не содержит partition key, можно получить overhead без выгоды.

### Индексы на partitioned tables

В PostgreSQL index на parent partitioned table создает partitioned index, а реальные индексы находятся на partitions.

Практические моменты:

- Глобальных индексов между partitions в PostgreSQL нет.
- Unique constraint на partitioned table должен включать partition key.
- Индексы надо проектировать с учетом локальных запросов к partitions.
- Индексы на каждой partition меньше и обслуживаются быстрее, чем один гигантский индекс.

Пример ограничения:

```sql
-- Обычно возможно, если partition key входит в unique constraint.
UNIQUE (tenant_id, external_id)
```

Если нужен глобальный уникальный `external_id` без `tenant_id`, придется решать отдельно:

- отдельная lookup table;
- UUID/ULID/Snowflake-like ID;
- application-level reservation;
- отказ от строгой глобальной уникальности.

### Constraints и foreign keys

Что помнить:

- Constraints на partitions помогают planner'у и защищают данные.
- Foreign keys с partitioned tables поддерживаются, но могут быть тяжелыми на больших объемах.
- Referential integrity между огромными partitioned таблицами надо проверять нагрузочными тестами.
- ON DELETE CASCADE на больших объемах может стать production incident.

### Maintenance

Partitioning часто внедряют ради эксплуатации больших таблиц.

Полезные операции:

- Создать будущие partitions заранее.
- Быстро удалить старые данные через `DROP TABLE`/`DETACH PARTITION`.
- Архивировать detached partition.
- Делать `VACUUM`, `ANALYZE`, `REINDEX` точечно.
- Загружать bulk data в staging table и затем `ATTACH PARTITION`.

Частые ошибки:

- Не создана partition для будущих данных, запись падает.
- Default partition незаметно разрастается.
- Слишком много partitions: планирование запросов и DDL становятся дорогими.
- Partition key выбран не по реальным запросам.
- Приложение фильтрует через функцию и ломает pruning.

Мини-чеклист PostgreSQL partitioning:

- Есть ли фильтр по partition key в главных запросах?
- Сколько partitions будет через 1, 3, 5 лет?
- Как создаются future partitions?
- Как удаляются/архивируются старые partitions?
- Нужны ли unique constraints, и входят ли в них partition keys?
- Проверены ли `EXPLAIN (ANALYZE, BUFFERS)` до и после?
- Есть ли мониторинг default partition и количества строк по partitions?

## 4. Partitioning vs sharding

Table partitioning:

- Одна логическая БД/кластер.
- PostgreSQL сам выбирает partition.
- Транзакции остаются локальными в рамках одного кластера.
- Хорошо для больших таблиц, retention, pruning, локальных индексов.
- Не решает полностью проблему одного primary для записи.

Sharding:

- Данные распределены по независимым узлам/кластерам.
- Приложение или middleware выбирает shard.
- Запись масштабируется горизонтально, если shard key распределяет нагрузку.
- Cross-shard операции становятся сложными.
- Нужны отдельные backups, migrations, failover, observability по каждому shard.

Короткий senior-ответ:

> Partitioning делит таблицу внутри одной базы, sharding делит данные между базами. Partitioning упрощает работу с большой таблицей, sharding масштабирует capacity, но переносит часть ответственности в приложение и операционную платформу.

## 5. Репликация

Репликация копирует изменения с primary на standby/replica.

Цели:

- High availability.
- Read scaling.
- Disaster recovery.
- Zero/low-downtime maintenance.
- Аналитические или ETL-потоки.

### Physical replication

Physical replication копирует WAL/страницы на уровне storage representation.

В PostgreSQL это основной механизм streaming replication.

Плюсы:

- Надежная и зрелая HA-модель.
- Реплика почти идентична primary.
- Хорошо подходит для failover.

Минусы:

- Обычно реплицируется весь кластер/база на физическом уровне.
- Нельзя гибко реплицировать только часть таблиц как в logical replication.
- Версии и совместимость строже.

### Logical replication

Logical replication передает изменения на уровне строк/таблиц: `INSERT`, `UPDATE`, `DELETE`.

Плюсы:

- Можно реплицировать отдельные таблицы.
- Удобно для миграций, blue/green, data integration.
- Возможны разные major versions PostgreSQL при миграциях, с ограничениями.

Минусы:

- Не всегда покрывает DDL автоматически.
- Требует primary key или replica identity для корректных updates/deletes.
- Конфликты и schema drift надо контролировать.

### Sync vs async replication

Async replication:

- Commit на primary не ждет подтверждения реплики.
- Лучше latency и throughput.
- При падении primary можно потерять последние транзакции, которые не дошли до replica.

Sync replication:

- Commit ждет подтверждения standby.
- Меньше риск потери данных.
- Выше latency.
- При проблеме standby может замедлить или остановить запись, если неправильно настроено.

Короткий senior-ответ:

> Async дает производительность, но допускает RPO больше нуля. Sync уменьшает RPO, но увеличивает latency и связывает доступность записи с состоянием реплики. Выбор зависит от RPO/RTO и критичности данных.

### Streaming replication и read replicas

Streaming replication в PostgreSQL передает WAL с primary на standby почти в реальном времени.

Read replica:

- Принимает read-only запросы.
- Может отставать от primary.
- Может конфликтовать с long-running queries при replay WAL.
- Требует connection routing в приложении или proxy.

Типовые паттерны routing:

- Все writes идут на primary.
- Не критичные reads идут на replica.
- Reads после writes идут на primary.
- Sticky session/window: после записи пользователь некоторое время читает с primary.
- Для админки/отчетов допустим lag, для платежей и прав доступа обычно нет.

### Replication lag

Причины lag:

- Медленная сеть.
- Реплика слабее primary.
- Большие транзакции.
- Long-running queries на replica.
- Недостаточный WAL bandwidth или storage I/O.
- Lock/contention и heavy maintenance.

Последствия:

- Пользователь не видит только что созданные данные.
- Проверки прав/баланса/лимитов могут использовать устаревшие данные.
- Failover может потерять последние изменения при async replication.

Что мониторить:

- WAL write/flush/replay lag.
- Время задержки в секундах.
- Размер replication slots.
- Рост `pg_wal` из-за отставших consumers.
- Ошибки apply в logical replication.

### Failover

Failover: promotion standby в новый primary.

Ключевые вопросы:

- Кто принимает решение: человек, Patroni, cloud provider, orchestrator?
- Как клиенты узнают новый endpoint: DNS, VIP, proxy, service discovery?
- Что с незареплицированными транзакциями?
- Как вернуть старый primary без split-brain?
- Проверен ли runbook на практике?

### Split-brain

Split-brain: две ноды считают себя primary и принимают запись.

Почему опасно:

- Расходятся данные.
- Автоматически слить изменения часто невозможно.
- Нужно fencing/STONITH/quorum/lease-based лидерство.

Короткий senior-ответ:

> HA без fencing опасен. Важно не просто быстро поднять новый primary, а гарантировать, что старый primary не продолжит принимать запись.

## 6. Шардирование

Шардирование распределяет данные по нескольким независимым хранилищам. Каждый shard хранит часть данных.

### Когда sharding оправдан

Sharding стоит рассматривать, если:

- Один primary не справляется с write throughput.
- Таблица/индексы настолько велики, что maintenance и backups не укладываются в окна.
- Нужна изоляция tenants или регионов.
- Горизонтальное масштабирование чтения уже не решает bottleneck.
- Оптимизация схемы, индексов, запросов, batching и partitioning уже недостаточны.

Когда sharding преждевременен:

- Нет понятного bottleneck.
- Данные помещаются в один кластер.
- Команда не готова поддерживать routing, migrations, backups, consistency.
- Большинство бизнес-операций требуют cross-shard transactions.

### Стратегии шардирования

#### Range-based sharding

Пример: users `1..1_000_000` на shard A, `1_000_001..2_000_000` на shard B.

Плюсы:

- Просто понимать и отлаживать.
- Хорошо для range queries.
- Можно перемещать диапазоны.

Минусы:

- Hot shard при монотонном ключе.
- Неравномерное распределение при skew.

#### Hash-based sharding

Пример: `hash(user_id) % N`.

Плюсы:

- Хорошее равномерное распределение.
- Простая маршрутизация.

Минусы:

- Resharding при изменении N дорогой.
- Range queries почти всегда cross-shard.
- Нужен consistent hashing или virtual buckets для гибкости.

#### Directory-based sharding

Есть mapping service/table: `tenant_id -> shard_id`.

Плюсы:

- Гибкое перемещение tenants.
- Можно учитывать размер и нагрузку tenant'а.
- Удобно для enterprise SaaS.

Минусы:

- Directory становится критичной зависимостью.
- Нужны кеширование, HA и consistency mapping'а.

#### Tenant-based sharding

Каждый tenant или группа tenants размещается на shard.

Плюсы:

- Хорошая изоляция клиентов.
- Можно переносить крупных tenants отдельно.
- Удобно для compliance и noisy neighbor control.

Минусы:

- Крупный tenant может стать hot shard.
- Cross-tenant analytics сложнее.

### Выбор shard key

Хороший shard key:

- Есть почти во всех hot queries.
- Равномерно распределяет данные и нагрузку.
- Минимизирует cross-shard joins и transactions.
- Стабилен: редко или никогда не меняется.
- Имеет понятную бизнес-семантику.

Плохой shard key:

- Монотонный `created_at` или auto-increment `id` без защиты от hot shard.
- Поле, которое часто меняется.
- Поле с сильным skew: например, один tenant генерирует 80% нагрузки.
- Поле, которого нет в ключевых запросах.

Короткий senior-ответ:

> Shard key выбирают не только по равномерности данных, а по равномерности нагрузки и локальности бизнес-операций. Лучший ключ тот, который делает большинство транзакций single-shard.

### Resharding

Resharding: изменение распределения данных между shards.

Подходы:

- Big bang migration с downtime: проще, но редко приемлемо.
- Dual write: писать в старую и новую схему, затем переключить reads.
- Backfill + CDC: перенести исторические данные и догонять изменения.
- Virtual shards/buckets: `hash(key) -> bucket -> physical shard`, переносить buckets.
- Directory-based move: поменять mapping после переноса tenant'а.

Риски:

- Потеря или дублирование записей.
- Нарушение порядка событий.
- Cross-shard references.
- Долгий backfill влияет на production.
- Нужно уметь rollback или forward-fix.

Мини-чеклист resharding:

- Есть ли инварианты и reconciliation queries?
- Как блокируются или синхронизируются writes на переносимый диапазон/tenant?
- Как проверяется полнота backfill?
- Как откатывается routing?
- Что происходит с кешами, очередями, search indexes?
- Есть ли throttling и мониторинг нагрузки?

### Cross-shard queries

Типы cross-shard запросов:

- Scatter-gather: отправить запрос на все shards и объединить результат.
- Fan-out by subset: запросить несколько известных shards.
- Precomputed views: заранее поддерживать агрегаты.
- ETL в analytical store: ClickHouse/BigQuery/Redshift.

Проблемы:

- Высокая latency: ответ ограничен самым медленным shard.
- Partial failures.
- Pagination и sorting across shards сложны.
- Rate limits и connection pool pressure.

Практическое правило:

> OLTP-путь должен стремиться к single-shard операциям. Cross-shard аналитику лучше выносить в отдельные read models или analytical DB.

### Cross-shard transactions

Варианты:

- Избегать через правильный shard key и локальность данных.
- Saga/process manager с компенсирующими действиями.
- Outbox/inbox + idempotent consumers.
- 2PC/distributed transaction manager, если цена сложности оправдана.
- Eventual consistency с явным статусом операции.

2PC trade-offs:

- Более строгая атомарность.
- Блокировки и coordinator failure.
- Сложность recovery.
- Плохо масштабируется для высоконагруженного OLTP.

Короткий senior-ответ:

> В senior design я сначала стараюсь спроектировать aggregate boundaries так, чтобы транзакция была single-shard. Если нельзя, выбираю saga/outbox и явно объясняю consistency model. 2PC оставляю для узких случаев, где бизнес требует строгой атомарности.

### Global IDs

Задачи global ID:

- Уникальность между shards.
- Возможность routing или traceability.
- Сортировка по времени, если нужно.

Варианты:

- UUID v4: прост, но случайный и хуже для индексов.
- UUID v7/ULID: time-sortable, удобнее для индексов и логов.
- Snowflake-like ID: timestamp + node/shard id + sequence.
- Composite key: `(shard_id, local_id)`.
- Central sequence service: просто концептуально, но bottleneck/SPOF без HA.

Практический ответ:

> Для распределенной системы я предпочту UUID v7/ULID или Snowflake-like ID. Auto-increment внутри shard можно оставить как local id, но наружу лучше не отдавать без shard context.

## 7. Consistency trade-offs

Ключевые понятия:

- Strong consistency: чтение видит последние подтвержденные записи.
- Eventual consistency: система сходится со временем.
- Read-your-writes: пользователь видит собственные изменения сразу.
- Monotonic reads: пользователь не видит откат назад во времени.
- Causal consistency: причинно связанные события видны в правильном порядке.

Где возникают trade-offs:

- Read replicas и lag.
- Async replication и failover.
- Кеши.
- Sharding и cross-shard операции.
- Event-driven интеграции.

Senior-level framing:

> Я не говорю просто CAP. Я уточняю бизнес-инварианты: где нужна строгая консистентность, где достаточно eventual consistency, какой RPO/RTO, какая цена stale read и partial failure.

Примеры:

- Баланс, платеж, лимит: чаще strong consistency или single-writer aggregate.
- Лента новостей, счетчики просмотров: eventual consistency допустима.
- Права доступа: часто нужны свежие reads или короткий TTL кеша.
- Отчеты: lag в минуты может быть приемлем.

## 8. ClickHouse: distributed tables и replication basics

ClickHouse чаще используют для аналитики, логов, событий и агрегатов, а не как primary OLTP DB.

Основные сущности:

- `MergeTree`: базовое семейство движков для хранения.
- `ReplicatedMergeTree`: репликация таблицы между нодами.
- `Distributed`: logical table, которая распределяет запросы по shards/replicas.
- Shard: часть данных.
- Replica: копия shard для HA/read scaling.

Как работает на практике:

- Данные часто пишут в локальные `ReplicatedMergeTree` таблицы.
- `Distributed` таблица используется как entrypoint для запросов или insert routing.
- Для cluster metadata и coordination традиционно используется ZooKeeper или ClickHouse Keeper.

Trade-offs:

- Отличен для больших append-only аналитических объемов.
- Не замена PostgreSQL для сложных OLTP транзакций.
- Mutations/updates/deletes дорогие относительно append/read сценариев.
- Нужно проектировать partition key, order by, primary key под запросы.
- Distributed queries могут быть тяжелыми, если не фильтровать по shard/partition-friendly ключам.

Короткий senior-ответ:

> ClickHouse масштабирует аналитику через shards и replicas. `Distributed` таблица не хранит данные сама как обычная OLTP-таблица, а маршрутизирует запросы к локальным таблицам кластера. Схему надо проектировать под append и аналитические выборки.

## 9. Redis Cluster basics

Redis Cluster делит keyspace на 16384 hash slots. Slots распределяются между master nodes, у master могут быть replicas.

Важно:

- Key попадает в slot по hash.
- Multi-key операции работают только если keys в одном slot.
- Для этого используют hash tags: `user:{123}:profile`, `user:{123}:settings`.
- Failover продвигает replica в master.
- Cluster client должен понимать redirects `MOVED`/`ASK`.

Что это значит для PHP:

- Клиентская библиотека должна поддерживать Redis Cluster.
- Нельзя бездумно использовать multi-key операции на разных slots.
- Lua scripts ограничены ключами одного slot.
- Для locks/rate limits/session storage надо понимать consistency и failover semantics.

Короткий senior-ответ:

> Redis Cluster масштабирует Redis по hash slots, но не делает произвольные multi-key операции распределенно-транзакционными. Дизайн ключей становится частью архитектуры.

## 10. RabbitMQ: не база данных, но масштабирование очередей

RabbitMQ не стоит использовать как базу данных:

- Это message broker, а не долговременное queryable storage.
- Очередь хранит сообщения до доставки/ack, но не заменяет consistency model БД.
- Долгие очереди ухудшают производительность и recovery.

Где есть partitioning/scale notes:

- Несколько queues для partitioning нагрузки.
- Routing key/exchange направляет сообщения в разные queues.
- Competing consumers масштабируют обработку одной очереди, но порядок сохраняется не всегда так, как ожидают.
- Quorum queues дают надежность, но имеют write amplification.
- Sharding по tenant/user/order может сохранить локальный порядок обработки.

Практическое правило:

> Для надежной интеграции с БД используйте transactional outbox: сначала записать событие в БД в одной транзакции с бизнес-изменением, затем доставить в RabbitMQ асинхронно и идемпотентно обработать.

## 11. Application-level implications для PHP/Laravel/Symfony

### Routing connections

В приложении нужно явно понимать:

- Какая операция write, какая read.
- Какие reads должны идти на primary.
- Какие reads можно отправить на replica.
- Как выбрать shard по shard key.
- Что делать, если shard недоступен.

Laravel:

- Поддерживает read/write connections в database config.
- Для сложного sharding часто нужен свой connection resolver/repository layer.
- Важно не прятать shard key глубоко в Eloquent magic, иначе легко получить cross-shard N+1.

Symfony/Doctrine:

- Можно использовать несколько connections/entity managers.
- Для sharding лучше явно проектировать repository/service layer.
- UnitOfWork и lazy-loading могут неожиданно тянуть данные не с того connection.

Практическое правило:

> В распределенной БД shard key должен быть видим в application boundary: route/controller/command/job должны нести tenant_id/user_id/account_id, чтобы не угадывать shard внутри ORM.

### ORM pitfalls

Частые проблемы:

- Lazy loading вызывает запросы без shard key.
- Транзакция случайно охватывает несколько connections.
- Global scopes скрывают важные фильтры.
- Auto-increment IDs конфликтуют между shards.
- Queue job содержит только local id без shard context.
- Кеш ключи не включают shard/tenant/version.

Мини-чеклист для PHP-кода:

- Все команды и jobs содержат shard key.
- Репозитории явно принимают shard/tenant context.
- Read-after-write идет на primary или использует consistency token/window.
- Idempotency keys работают между retries.
- Outbox events содержат global ID и shard context.
- Connection pool/Max connections посчитаны на число PHP workers.

### Connection pooling

Для PHP-FPM важна модель соединений:

- Много PHP workers могут создать слишком много DB connections.
- PgBouncer часто нужен для PostgreSQL.
- В transaction pooling mode есть ограничения: session-level state, prepared statements, temp tables.
- Read replicas и shards умножают количество потенциальных connections.

Короткий senior-ответ:

> При шардировании проблема connections растет быстрее, чем кажется: workers × shards × replicas. Нужны pooling, лимиты, lazy connection и понятная стратегия routing.

## 12. Миграции схемы

Partitioning:

- DDL может применяться к parent и partitions, но надо проверять locks.
- Создание индексов лучше делать `CONCURRENTLY`, где применимо.
- Большие backfill лучше делать батчами.
- Future partitions должны получать актуальную схему.

Replication:

- Logical replication чувствительна к schema compatibility.
- DDL rollout должен учитывать publisher/subscriber.
- Backward/forward compatible migrations важны для rolling deploy.

Sharding:

- Миграции надо применять ко всем shards.
- Нужна таблица версии схемы на каждом shard.
- Миграции должны быть идемпотентными и наблюдаемыми.
- Ошибка на одном shard не должна оставлять систему в непонятном состоянии.

Безопасный порядок изменения поля:

- Add nullable column.
- Deploy code writing both old/new if needed.
- Backfill batches.
- Switch reads.
- Add constraints/indexes.
- Remove old field later.

## 13. Backups и disaster recovery

Ключевые метрики:

- RPO: сколько данных можно потерять.
- RTO: как быстро надо восстановиться.

PostgreSQL:

- Base backups + WAL archiving для point-in-time recovery.
- Регулярно тестировать restore, а не только создавать backup.
- Для replication slots следить за ростом WAL.
- Для partitioned tables можно архивировать detached partitions отдельно.

Sharded system:

- Backup должен быть согласован по shards или иметь понятную recovery model.
- Нужны metadata backups: shard map, schema versions, migration state.
- Восстановление одного shard может нарушить глобальную консистентность.
- Runbook должен описывать partial restore.

ClickHouse:

- Backup локальных таблиц и metadata.
- Проверить совместимость с replicated tables и cluster topology.
- Для аналитики часто допустим rebuild из source events, если events надежно сохранены.

Redis:

- RDB/AOF в зависимости от требований.
- Redis cache можно восстановить пустым, Redis как state store требует более строгого DR.

Senior-level answer:

> Backup без регулярного restore-теста не является backup strategy. Для shards важны не только данные, но и shard map, порядок восстановления и проверка инвариантов после restore.

## 14. Observability

Что мониторить в PostgreSQL:

- QPS, latency, slow queries.
- `EXPLAIN` для hot queries.
- Locks, deadlocks.
- Connections, pool saturation.
- Replication lag.
- WAL generation rate.
- Autovacuum activity и table/index bloat.
- Cache hit ratio, I/O wait.
- Rows per partition, default partition growth.

Что мониторить в sharded system:

- Load per shard.
- Hot tenants/users.
- Cross-shard query rate.
- Routing errors.
- Per-shard migration version.
- Per-shard backup age.
- Queue lag per shard/tenant.
- Error budget по partial failures.

Application metrics:

- Read from primary vs replica ratio.
- Read-after-write fallback count.
- Retry count and idempotency conflicts.
- Outbox pending age.
- Job processing lag.
- Cache hit/miss by key group.

## 15. Common pitfalls and trade-offs

- Масштабируют БД до анализа query plans и индексов.
- Выбирают sharding без понимания главных бизнес-транзакций.
- Используют replicas для reads, но забывают read-after-write.
- Делают partitioning, но запросы не фильтруют по partition key.
- Создают слишком много partitions.
- Не создают future partitions.
- Не тестируют failover и restore.
- Не учитывают connection explosion в PHP-FPM.
- Используют global auto-increment ID в sharded architecture.
- Делают cross-shard joins в hot path.
- Путают RabbitMQ с durable database.
- Не закладывают resharding и metadata management.
- Игнорируют skew: средняя нагрузка нормальная, один tenant кладет shard.

## 16. Senior-level short answers

### Когда partitioning, а когда sharding?

Partitioning: если проблема в размере таблицы, retention, pruning, локальном maintenance. Sharding: если нужно распределить write/read capacity между независимыми узлами или изолировать tenants/regions.

### Почему read replicas не масштабируют запись?

Потому что запись все равно идет на primary. Реплики помогают чтению и HA, но не увеличивают write throughput primary.

### Как бороться с replication lag?

Мониторить lag, ограничивать long-running queries, правильно sizing replica, читать критичные данные с primary, использовать sticky read-after-write, оптимизировать большие транзакции и WAL throughput.

### Чем опасен async failover?

Последние подтвержденные клиенту транзакции могли не дойти до replica. После promotion они потеряются или потребуют reconciliation.

### Как выбрать shard key?

По локальности транзакций, равномерности нагрузки, стабильности ключа и присутствию ключа в hot queries. Не только по равномерности количества строк.

### Как делать транзакции между shards?

Лучше избегать. Если нельзя: saga/outbox/idempotency/eventual consistency. 2PC использовать только при строгой необходимости и понимании operational cost.

### Почему UUID v7/ULID лучше UUID v4 для многих БД?

Они примерно сортируются по времени, что уменьшает random insert pattern в B-tree индексах и упрощает диагностику по времени создания.

### Как Laravel-приложению жить с read replicas?

Разделить read/write connections, критичные reads после writes направлять на primary, учитывать transactions, кеши и jobs. Не полагаться слепо на ORM, если нужна строгая consistency.

## 17. Мини-практика

### Практика 1: таблица событий на 5 млрд строк

Задача: `events(user_id, type, created_at, payload)`, частые запросы за последние 7/30 дней, retention 13 месяцев.

Возможное решение:

- PostgreSQL range partitioning по `created_at` месячно или недельно.
- Индексы на partitions под hot queries: `(user_id, created_at)` или `(type, created_at)`.
- Future partitions через scheduled job.
- Retention через `DROP/DETACH PARTITION`.
- Старые данные архивировать или переносить в ClickHouse/S3.
- Проверить pruning через `EXPLAIN`.

### Практика 2: SaaS с крупными tenants

Задача: 10 000 tenants, 5 из них дают 60% нагрузки.

Возможное решение:

- Tenant-based или directory-based sharding.
- Крупных tenants выделять на отдельные shards.
- Shard map с HA и кешированием.
- Все jobs/events содержат `tenant_id`.
- Cross-tenant analytics в ClickHouse.
- План resharding tenant'а заранее.

### Практика 3: read-after-write баг

Симптом: пользователь создал заказ, сразу попал на страницу заказа, а там 404.

Вероятная причина:

- Запись ушла на primary, чтение ушло на lagging replica.

Исправления:

- Читать заказ после создания с primary.
- Sticky primary reads на короткое окно.
- Consistency token/LSN-aware routing, если инфраструктура поддерживает.
- UI pending state, если eventual consistency допустима.

### Практика 4: cross-shard перевод денег

Задача: перевести деньги между счетами на разных shards.

Вопросы:

- Можно ли shard по account group так, чтобы связанные счета были вместе?
- Нужна ли строгая атомарность или допустим pending/settlement process?
- Как реализовать идемпотентность операции?
- Как будет работать reconciliation?
- Какой audit log является source of truth?
